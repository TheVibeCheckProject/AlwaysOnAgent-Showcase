## 1. Chat tokens (the cost of every message)

### What a chat call costs today (measured, 87 chat calls in the last 7 days)

| Part of the prompt | Avg tokens | Share |
|---|---|---|
| Persona (`ASSISTANT_PERSONA`) | 3,212 | 58% |
| Tool descriptions (core + routed groups + `more_tools`) | 2,187 | (sent alongside) |
| Conversation history (uncompressed) | 1,594 | |
| Older summaries | 819 | |
| Archive matches | 262 | |
| Facts | 277 | |
| Profile, live status, time, reminder, recent summary | ~800 | |
| **Prompt, median / 90th percentile** | **5,509 / 6,229** | |

- 36 of the 87 calls were a **second, third or fourth tool round**, each resending the whole prompt. So any saving in
  the fixed parts counts about 1.4 times per reply.
- Only 18% of input tokens were served from Gemini's implicit cache. Google lists a **4,096-token minimum** for
  implicit caching on 3.6/3.8 Flash. On the free tier this saves no money, so shrinking the prompt beats chasing the
  cache.

### T1. The persona explains every tool group on every message (≈ −1,300 to −1,600 tokens per call)

`ASSISTANT_PERSONA` is 3,280 tokens. Its **"How you work" section is 2,313 of them**, and most of that describes tool
groups that usually aren't loaded for the reply:

| Persona paragraph | Tokens | Its tools sent only with group |
|---|---|---|
| Actions (render, TikTok, pins, AgentWork, cancel, research) | 385 | videos, stats, projects, web |
| propose_project | 124 | projects |
| Reaching out first / Sunday review | 135 | schedules |
| Schedules | 96 | schedules |
| The computer | 94 | computer |
| Canvas | 90 | canvas |
| Zoho Mail | 83 | mail |
| Images (`/image`, recent prompts) | 83 | files |
| Email, "On email" | 117 | mail |
| Watches, follow-ups | 122 | watches |
| Calendar/Drive, texts and calls, lists | 167 | calendar, drive, phone, lists |
| **Total that only matters when its group is loaded** | **≈ 1,500** | |

The architecture paragraph at the top of "How you work" (440 tokens: the mini PC, the database tables, the threads)
only matters when Alex asks how the agent works.

**Fix (recommended):** move each paragraph into a `GROUP_GUIDE` dictionary keyed by tool group. `tool_specs()`
appends the guides of the groups it sends, as one short system block placed **after** the stable persona (and
`more_tools` adds its group's guide too). The persona keeps the truth rules, how to talk, memory, the core tools,
`ask_user`, `propose_task` and a 2-line "what I am". Answer "how do you work" questions with `read_project_file` on
this file, which the persona already allows. `tests/test_persona_claims.py` keeps working if it reads persona plus
all guides.
- Expected: persona ≈ 1,700 tokens. A typical reply sends 0 or 1 group guide (≈ 100 tokens), so about **−1,400 per
  call, −25% of the chat prompt**.
- This is the same idea as Anthropic's tool search, Spring AI's tool discovery and TanStack's lazy tools: send only
  what the request needs. Their measurements show 34–64% fewer tokens with no loss of capability.

### T2. Always-sent tool descriptions (≈ −450 tokens per call)

The core group is 1,286 tokens, plus `more_tools` at **450 tokens**, the single biggest tool, because its description
lists every group in full.
- **`more_tools`:** give it the group names as an enum with a 2–4 word label each (≈ 120 tokens). The router already
  chose groups; `more_tools` is the fallback, used in 33 of 332 replies.
- **Move `connect_google` (82) to the mail, calendar and drive groups:** it's only useful there.
  **Move `background_status` (82) to the schedules group:** that's where the proactive and away-shift tools live.
- **Shorten `look_into` (165) to about 90 tokens.** It was added today.
- Expected: about **−450 tokens per call**.

### T3. Gemini Flash thinks by default, and it stalls replies (latency, and wasted quota)

`CloudLLM._prepare` sets `reasoning_effort` only for gpt-oss. Gemini routes get the model's default. Google's
thinking docs list **3.8 Flash at "medium" by default**, 3.6 Flash at medium, and 3.5 Flash-Lite at minimal. This
week every chat attempt on 3.8 Flash failed (3 timeouts at 20 s, 1 overload), each timeout adding 20 s to a reply
that Flash-Lite had already failed.

**Fix:** in `_prepare`, for `gemini-3*` chat routes send `reasoning_effort: "low"` (or `"minimal"` where supported:
3.5 Flash-Lite, 3.6 Flash). Gemini's OpenAI-compatible endpoint maps it to `thinking_level`. Then measure 3.8 Flash
again before deciding its place in `CHAT_MODELS` (Alex's rule: measure before moving models).

### T4. An empty reply after a tool call skips to the next model (2 this week)

Twice yesterday (20:51 and 21:31) 3.5 Flash-Lite answered a tool round with **no text** (logged as "garbage",
0.0 s). The chat then tried 3.8 Flash (20 s timeout) before 3.1 Flash-Lite answered. Google's developer forum has
many reports of Gemini 3.x returning an empty turn after a function response. The workaround reported to work is a
short text part sent with the function results, plus checking `finish_reason`.

**Fix:** when a tool round ends with empty text on a route that just worked, retry **the same route once** with a
short nudge ("Now answer the user in one or two sentences.") before moving on. When the last tool was a card or
question tool (`ask_user`, `propose_*`, `computer_task`), fall back to a fixed line ("Tap the card above when
ready.") instead of another model call.

### T5. Smaller wins

- **Older summaries average 819 tokens** (budget 900): `_summary_block` adds them by similarity with no minimum
  score. Add a minimum similarity (like `VEC_MIN_ARCHIVE_KEYWORD`) and a 500 budget. Measure with
  `scripts/eval_memory.py` first.
- **The memory extract call (≈ 2,300 tokens) runs after most chat turns** (51 this week). It already skips trivial
  messages. Batching it every few turns, or during the lull the proactive cycle already waits for, would roughly
  halve it. Lower priority: it doesn't slow replies.
- **DeskAI uploads the last 10 messages and a system prompt with every send** (`streamAlwaysOnAgentChat`: `system`,
  `history`, `prompt`). The server ignores them (`ChatRequest` has no such fields), so they cost bytes, not tokens.
  Remove them.

## 2. Security

### S1. CRITICAL: the vault lock can be bypassed (DeskAI)

`CredentialsVaultDialog.kt` shows **"Reset Pattern Lock" while the vault is locked**. It deletes
`vault_pattern_hash` with no check, and the user is then asked to set a new pattern and is let in. The lock protects
nothing.

Smaller issues with the same lock:
- The pattern hash is a fixed-salt SHA-256 over under a million possible patterns (4 to 9 of 9 dots). Anyone who
  can read the app's storage reverses it in seconds.
- There's no attempt limit.
- The lock only guards the phone's screen: the server's `/api/computer/credentials` accepts any request with the
  token.

**Fix (recommended, and it's the "native" option):** replace the custom pattern with Android's own
**BiometricPrompt** using `setAllowedAuthenticators(BIOMETRIC_STRONG or DEVICE_CREDENTIAL)` (androidx.biometric).
This gives fingerprint or face, falling back to the phone's own PIN, pattern or password. Nothing to store,
Android handles lockout, and it looks like every other app.
- Android 10 and lower can't combine the two; there, check `KeyguardManager.isDeviceSecure()`.
- If the custom pattern stays, the minimum fix: remove Reset from the locked screen, allow reset only after a
  BiometricPrompt, add a 5-try lockout, and use a slow hash with a random per-install salt.

### S2. HIGH: passwords typed in chat reach the cloud model

On 2026-10-26 Alex typed the demo Google account's password into chat (message #1337), and the model replied "I've
securely noted the password".
- The chat catches Google and Zoho sign-in pastes before any model (`GOOGLE_SIGNIN`, `ZOHO_CODE`), but **nothing
  catches a password**. `redact_secrets` only replaces values from `.env`.
- The stored copy now reads `[REDACTED]`, and so does the 03:00 backup. Nothing in the code or git history explains
  who redacted it. The model most likely saw the original: the message went to it before being stored, and
  nothing in the chat path redacts passwords.
- Gemini's free tier may use prompts to improve Google's products, and those terms were accepted. **Treat that
  password as exposed: change it.** It's a throwaway account, so the damage is small.

**Fix:** a pre-model intercept next to the sign-in ones in `chat.py`:
- **Patterns:** "password is …", "pw: …", "pass: …", "the code is …", and a word after "password" that mixes
  letters, digits and symbols (AgentComputerUse's `activity.secret_like` already has this test).
- **On a match:** store nothing, send nothing to a model. Reply "That looks like a password: I didn't send it to the
  AI. Save it in the Vault (🔐) instead", with a chip that opens DeskAI's vault pre-filled.
- **Design note:** published redaction tools agree that regexes catch token formats but miss conversational
  passwords, and recommend layering (pattern rules plus a contextual check). Here the contextual check must stay
  local (never a cloud model). The phrase rules plus `secret_like` are enough for the one user who types them.
- **DeskAI side:** the chat box can warn before sending when the text matches the same rules.

### S3. MEDIUM: AgentComputerUse saves passwords on its own (commit `175063a`)

`owner.py _auto_save_credential` saves any password answered through Needs you or Take over to Windows Credential
Manager. Problems:
- **It saves before knowing the login worked:** a mistyped password is saved and autofilled on every later run.
- **The domain is a guess:** it takes the host's last two labels, which is wrong for `co.uk`-style suffixes and for
  single-sign-on pages.
- **The username is a guess:** the first email address in the goal text (which may be someone else's), else
  `"default"`.
- **Failures vanish:** `except Exception: pass` hides them.
- **No tests, and no CHANGELOG entry.** Neither `175063a` nor AlwaysOnAgent `cab7728` (the vault API) has one.

**Fix:** keep the password in memory until the run sees the sign-in succeed, then send a Needs you choice "Save this
password for google.com (alwaysonagentlite@…)? Save / Don't save". Use a public-suffix list for the domain (the
`tldextract` package), log failures (never the password), and add tests. Also: the vault API's `password.strip()`
changes passwords that start or end with a space; drop the strip.

### S4. MEDIUM: the HUD token crosses home Wi-Fi in plain HTTP

DeskAI talks to `http://192.168.x.x:8080` (`usesCleartextTraffic="true"`). The token in that header controls Take
over (the Mini's real mouse and keyboard), the credential vault, tasks and the memory. Anyone on the home Wi-Fi can
read it. Tailscale traffic is already encrypted.

**Fix:** turn on Tailscale's HTTPS certificates (MagicDNS name `agent-mini.<tailnet>.ts.net`) and put
`tailscale serve` in front of port 8080. That's tailnet-only, not Funnel, with automatic Let's Encrypt certificates.
Then DeskAI can use that one HTTPS address at home and away, which also simplifies the LAN/remote failover. Keep
plain LAN HTTP only as an opt-in fallback, through a `network_security_config` that allows cleartext for that one
IP.

### S5. LOW–MEDIUM: DeskAI keeps the token unencrypted and allows cloud backup

- The token is in the Room table `bridge_config`, as plain text.
- `allowBackup="true"`, and `backup_rules.xml` / `data_extraction_rules.xml` are still Android Studio's commented
  samples, so Android backs up everything, including the token and the chat history.

**Fix:** exclude the database and the vault prefs from cloud backup and device transfer in both rule files. Store the
token encrypted with an Android Keystore key (AES-GCM), or DataStore with the `datastore-tink` artifact. Don't use
EncryptedSharedPreferences: androidx `security-crypto` is deprecated.

### S6. LOW: `/api/chat` sends `Access-Control-Allow-Origin: *`

`chat_endpoint` sets wildcard CORS headers, while API.md says "CORS: none on purpose". The token still protects it,
since a browser can't add the header without a preflight the server doesn't approve. But it contradicts the
documented policy. **Fix:** remove the three header lines.

## 3. Reliability and correctness

### R1. One message can be answered twice (DeskAI failover)

`executeWithFailover` re-sends `POST /api/chat` to the Tailscale address when the home address throws, **including
after the server already received it**: a read timeout (120 s) or Wi-Fi dropping mid-reply. The server uses
`turn_id` only for cancelling, so the message is stored twice and answered twice (double tokens, two replies).

**Fix:** server-side idempotency on `turn_id`, the same pattern as the `Idempotency-Key` that tasks already have:
- keep `{turn_id: future}` for 10 minutes;
- a repeat waits for and returns the first reply instead of starting a new turn.
DeskAI already sends a stable `turn_id` per message.

### R2. A failed task's real error is hidden from the chat

For task-231, `last_error` was the generic "Engine 'computer' failed with exit code: 1". The actual reason
("JSONDecodeError: Extra data") was only in `output_summary`. `format_task_row` (used by `list_tasks`) shows only
`last_error`, so when Alex asked "What's that error?" the chat had nothing real and invented "no active execution
session or browser driver".

**Fix:**
- The daemon stores the real reason as `last_error` when a run returns one: `daemon.py` has it as the text it
  returns.
- `format_task_row` falls back to the first line of `output_summary` for failed tasks.
- Add a test with a computer task that fails like task-231.

### R3. `keep_promise` will start the background helper by mistake (added today, my own bug)

`PROMISE` matches "I'll check … and let you know", which is the natural wording after a mail watch or schedule ("I'll
check every 5 minutes and let you know"). Since `watch_mail` and `create_schedule` aren't in `PROMISE_BACKED_BY`, such
a reply would start a needless helper and add "I've started looking into it".

**Fix:** add `watch_mail`, `change_watch`, `create_schedule`, `change_schedule`, `proactive_settings` and the
`propose_*` card tools to `PROMISE_BACKED_BY`. Add those phrasings to `FINE` in `tests/test_follow_up.py`.

### R4. 3.8 Flash is the second chat model but never answered this week

4 chat attempts, 0 answers (3 timeouts, 1 overload). With T3's reasoning setting it may recover. If it doesn't,
moving it below 3.1 Flash-Lite would save 20 s on every reply where Flash-Lite fails. Measure first, per the handoff.

### R5. The chat can't find what a computer run saved

Every run keeps its step screenshots at `AgentComputerUse\data\runs\<run id>\step-NN.jpg` (task-233: 18, in
`20261026-212256`). But the run id isn't in the task result, so the chat guessed a location.

**Fix:** put the run id, screenshot count and folder in the computer result (`computer_use.describe`), so `get_task`
shows them. A later step could have DeskAI show them in the task's details.
- **Privacy:** the last screenshots of task-233 show the new API key, and runs are kept 14 days.
- The zoomed, highlighted tutorial screenshots Alex asked for don't exist yet. That's a feature (crop around the
  clicked element, draw a ring), not a bug.

### R6. Smaller items

- **Updater:** checks only that the downloaded APK is over 1 MB. Compare it with `fileSizeBytes` (already in
  `version.json`), and better, add a `sha256` field. Android's signature check already blocks a tampered APK; this
  gives a clean "download incomplete, retrying" instead of an install error.
- **DeskAI has 7 unit test files for 22,000 lines.** The pattern-lock gesture bug (fixed today) was the kind a
  Compose UI test catches: down → move without lifting → pattern completes.
- **The truncated message "Don't do anything just yet b"** (yesterday 21:00) wasn't a code bug: the chat box sends
  only on the send button, so it was most likely an early tap.
- **`/status` loads up to 1,000 facts just to count them** (`list_facts(limit=1000)`). Use a COUNT query.
